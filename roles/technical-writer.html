Technical Writer

An AI employee that keeps the docs in sync with what actually shipped, and turns support threads into pages people can find.

Documentation rots in a specific way. A feature ships, the docs do not change, and six months later the docs describe a product that no longer exists. Nobody is at fault; the person who shipped the feature had a deadline and the writer was not in the room.

An AI employee fixes the sync problem rather than the writing problem. It watches what ships, drafts the doc change, and opens it for review alongside the code. It also does the other high-value job: reading support threads and turning the recurring questions into pages, which is documentation written from evidence rather than from imagination.

What it handlesFour use cases this role is actually scoped for.

  • Docs updates from changelogs

    Reads merged changes and release notes, works out which documentation pages are now wrong, and drafts the update. Opens it as a reviewable change rather than editing live docs.

  • Support thread to documentation

    Clusters recurring support questions and writes the page that answers each one, in the words customers actually use. Documentation driven by real questions rather than by the org chart.

  • API reference maintenance

    Keeps parameter tables, examples and error codes in sync with the code, and flags endpoints that are documented but no longer exist.

  • Onboarding and runbook writing

    Turns a series of meetings, tickets and code into a runbook someone can follow at 3am. The documentation nobody writes until an incident forces it.

Scope and access

What it does

  • Drafts documentation updates from merged changes and release notes.
  • Turns recurring support questions into published pages.
  • Maintains API references, examples and error code tables.
  • Writes runbooks and onboarding guides from existing material.
  • Flags documentation that contradicts the current product.
  • Keeps a changelog that is readable by customers rather than by engineers.

What it needs

  • Read access to the repository, the issue tracker and the support system.
  • Write access to docs as pull requests, not direct edits.
  • A style guide, or the docs will read inconsistently across pages.
  • A reviewer who knows the product.

What stays humanThe boundary is the design, not a limitation.

Not delegated

  • Approving documentation changes, especially anything about security or pricing.
  • Deciding what to document and what to leave to support.
  • Judging whether an explanation is actually clear.
  • Anything that makes a commitment about future behaviour.

Fit

Good fit if

  • You ship regularly and the docs lag behind.
  • Support answers the same questions repeatedly.
  • You have a docs site with a review process.

Not a fit if

  • You have no documentation at all. Write the first ten pages yourself.
  • Nobody reviews docs changes, so wrong pages will go live.
  • Your product changes so fast that docs are obsolete on arrival. Fix the release process first.

Questions people ask

Will the docs sound generic?

They will if it has no style guide and no examples of your existing docs. Give it both, and give it the actual support threads, and the writing becomes specific because the input is.

Can it write API references?

Yes, and this is one of its strongest uses because the source of truth is the code. It is much better at keeping a reference accurate than at explaining a concept clearly.

Does it replace a technical writer?

It replaces the maintenance, which is most of the hours. The writer keeps the information architecture and the judgement about what a reader needs, which is the part that makes docs usable.
