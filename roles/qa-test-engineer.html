Engineering & Product

QA / Test Engineer

An AI employee that writes the tests nobody wrote, reproduces the bugs nobody could, and keeps the suite honest.

Every codebase has the same gap: the paths that are tested are the ones that were easy to test, and the paths that break in production are the ones nobody wrote a test for. Not from laziness, but because writing a test for an awkward path takes an hour and the sprint does not have an hour.

An AI employee is good at exactly that hour of work. It reads the code, works out what the untested branches are, and writes the tests. It also does the other half of QA that consumes time: turning a vague bug report into a reproducible case, and working out why a test is flaky. What it should not do is decide that a change is safe to ship. That is a human judgement, and the role is scoped so a human always merges.

What it handlesFour use cases this role is actually scoped for.

  • Test coverage for untested paths

    Reads the code, identifies branches and error paths with no coverage, and writes tests for them. Prioritises by what would actually break in production rather than by what is easy to cover.

  • Bug reproduction from reports

    Takes a support ticket or a vague report, works out the reproduction steps, writes a failing test that demonstrates the bug, and attaches it to the issue. Turns 'it does not work' into something a developer can fix.

  • Flaky test triage

    Identifies tests that fail intermittently, works out whether the cause is timing, ordering, shared state or a real race condition, and proposes a fix. Flaky suites get ignored, and an ignored suite is worse than none.

  • Regression test from incidents

    After an incident, writes the test that would have caught it, so the same failure cannot return silently.

Scope and access

What it does

  • Writes tests for uncovered branches and error paths, prioritised by production risk.
  • Reproduces reported bugs and attaches a failing test to the issue.
  • Triages flaky tests and proposes fixes.
  • Writes regression tests from post-incident reviews.
  • Reviews pull requests against a test checklist and flags missing coverage.
  • Maintains test fixtures and reports suite health over time.

What it needs

  • Read access to the repository and the CI system.
  • A test framework and a convention for where tests live.
  • A rule that it opens pull requests rather than pushing to main.
  • Access to the issue tracker so it can link tests to bugs.

What stays humanThe boundary is the design, not a limitation.

Not delegated

  • Merging. Always a human.
  • Deciding what level of coverage is enough.
  • Judging whether a test asserts the right behaviour, which requires product intent.
  • Release sign-off.

Fit

Good fit if

  • You have a test suite and known coverage gaps.
  • Bug reports arrive vague and cost developer time to triage.
  • Your CI is reliable enough to run the tests it writes.

Not a fit if

  • You have no tests at all. Start with a framework and a convention first.
  • Your build is so slow that more tests make it unusable.
  • You want it to merge its own work. Do not.

Questions people ask

Will it write good tests?

It writes tests that pass, which is not the same thing. Review them for whether they assert the right behaviour. The common failure is a test that asserts the current implementation rather than the intended behaviour, which then blocks a correct change.

Can it fix the bugs too?

It can propose a fix, and sometimes the proposal is good. The value is highest when it stops at the reproduction, because that is the part humans skip and the part that makes the fix fast.

Does it replace a QA engineer?

It replaces the writing of routine tests and the triage. The QA engineer still owns strategy, what to test, and the judgement about risk.
